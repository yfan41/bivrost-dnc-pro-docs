## 前提：改动通常是对的 {#premise}

操作工在控制面板上调进给、调转速、改切深，绝大多数时候是**基于现场判断的正确改动**。
问题从来不是"他们不该改"，而是"改了之后没人知道"。

所以 DNC Pro 的姿态是：**捕获它，摆出来，让工程师决定。绝不悄悄还原。**

## 捕获 {#capture}

[滚动镜像](/guide/mirror/)发现某个**受管**文件的内容和 DNC Pro 期望的不一致时：

1. 把机床上的当前内容存成一个新版本，来源标记为**机边捕获**，状态是**草稿**
2. 建一条**机边修改**记录，状态"待处置"
3. 触发 `drift.captured` Webhook
4. 在导航栏角标、总览页卡片、机边修改队列上计数

"期望的内容"是这样解析的（取最新的一项）：

- 若已有一条未处置的机边修改 → 期望就是那次捕获的内容（**后续再改只更新同一条记录**，不会刷屏）
- 否则取三者中最新的：上一次被采纳的机边修改 / 上一次成功下发的回读内容 / 采纳基线

未受管文件**不参与**这套逻辑——它们被备份，但从不被检查。

## 处置 {#disposition}

**机边修改**页列出队列，点进去看差异：

![机边修改处置](/img/console/drift-detail.png)

<p class="shot-caption">v1（已下发）→ v2（机边修改）的差异；意见必填；驳回时是否推回机床是一个要单独勾选的动作</p>

| 处置 | 发生什么 |
| --- | --- |
| **采纳修改** | 捕获的版本进入**正常发布流程**（提交审批 → 放行）。**机台保持现状**，不发生任何传输 |
| **拒绝修改** | 捕获版本作废。可选**并将已发布版本推回机台**——这是一次显式勾选，**绝不自动执行** |

两条路径的共同点：**机床上的内容只有在人明确要求时才会被改动。**

### 采纳的完整链路 {#accept-flow}

```text
操作工改了 → 镜像捕获（草稿·机边捕获）→ 工程师采纳
   → 进入审批队列 → 审批人批准 → 已发布
   → （可选）重新下发到其他同型机床，让整个机组收敛到这一版
```

这条链路把"某台机床上的一个私下改动"变成"整个机组的一次工艺改进"，
而且全程有据可查。

### 拒绝并推回 {#reject-pushback}

勾选"推回机台"后，系统对这台机床执行一次完整的[事务式下发](/guide/transfer/)，
把当前已发布版本写回去。它会出现在传输记录里，和普通下发没有区别。

不勾选则只是关掉这条记录，机床上的内容**保持被改过的样子**——
适用于"这个改动我知道了，先这么跑，正式版本另行安排"的情况。

## 试制期间不告警 {#trial}

进行中（含已过期未处置）的[试制](/guide/trials/)会抑制该文件的漂移捕获——
试切期间调参数是预期行为，不该每改一次就报一条。

改动本身仍被镜像完整备份。

## 队列长什么样 {#queue}

![机边修改队列](/img/console/drift.png)

每条记录给出：机台、文件名、对应程序、检测时间。
总览页的"待处理机边修改"卡片列出最近几条并直接跳转。

## 谁能处置 {#permissions}

需要 `drift.disposition` 权限，属于 `编程员` 和 `管理员`。
授权范围可按机组或程序库限定。

**审批员和操作工没有这个权限**——处置漂移是工艺决策。

## 一个健康的车间是什么样 {#healthy}

机边修改队列**不应该长期为空**。为空通常意味着两件事之一：

- 你的程序确实已经很成熟（少见但可能）
- 操作工发现改了也没用/会被覆盖，干脆不改了（常见，而且是坏事）

队列里稳定有几条、并且被及时处置，说明这条反馈通道是活的。
