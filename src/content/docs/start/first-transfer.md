---
title: "4.3. 第一次下发"
description: 建库 → 建程序 → 上传 → 审批 → 绑定机台 → 下发，走通一条完整链路
---

这一节走通一条最短但不偷工减料的链路：让一个程序从上传走到机床上，并通过回读校验。

## 第一步：建一个程序库 {#library}

**程序库 → 新建程序库**。程序库是**审批策略**的单位，一个车间通常需要 2–3 个：

| 程序库 | 典型策略 | 适用 |
| --- | --- | --- |
| 量产程序库 | 1 人审批 · 禁止自审自批 · 需人工放行 | 已量产零件，改动要有第二双眼睛 |
| 试制程序库 | 1 人审批 · 允许自审自批 · **自动放行** | 新品试制期，工程师需要快速迭代 |
| 工装与对刀库 | **2 人审批** · 禁止自审自批 · 需人工放行 | 所有机床共用的宏与子程序，出错面大 |

三个开关的含义：

- **审批人数**：需要几个不同的人批准才能放行
- **禁止自审自批**：作者本人不能批准自己写的版本（**默认开启**）。
  单人小厂可以关掉它，或者干脆用自动放行
- **自动放行**：提交即发布，不进审批队列

:::tip[职责分离是默认值]
"作者不能批自己"是 DNC Pro 的默认姿态。这不是繁文缛节——
它是把"我改完顺手就发了"这个最常见的事故来源关掉。
:::

## 第二步：建程序并上传第一版 {#program}

**程序库 → 新建程序**。程序的身份由这几项构成：

| 字段 | 说明 |
| --- | --- |
| 名称 | 人看的名字，例如 `泵体 · 粗铣外形` |
| 零件号 | 例如 `HX-2043` |
| 工序 | 例如 `OP10` |
| 适用机型 | 例如 `FANUC 31i`、`FANUC 0i-F`——提示性信息，帮助选机台 |
| 说明 | 一句话讲清这个程序干什么 |

建好之后在程序详情页点**上传新版本**，选文件并写一条**备注**。

:::tip[备注是给三个月后的自己看的]
"改了参数"没有意义。"切深 2.5→3.0mm，走刀 300→260，配合新牌号刀片提效"
——三个月后有人问起这版为什么这么走，答案就在这里。
:::

![程序详情](/img/console/program-detail.png)

上传后版本处于**草稿**状态，只有作者和有权限的人看得到，**不能下发**。

## 第三步：提交审批并放行 {#approve}

在版本行点**提交审批**，版本进入**待审批**。

审批人（有 `审批员` 角色的人）在**审批**页看到队列，点**审阅**：

![审批评审](/img/console/approval-review.png)

<p class="shot-caption">评审弹窗默认展示与上一版的差异，也可以切到「查看完整程序」；意见必填</p>

批准后：

- 若已达到程序库要求的审批人数 → 版本变为**已发布**，可以下发
- 若还差人 → 停在待审批，界面上显示"已获 N 次批准"

驳回则退回草稿，作者修改后重新提交。

:::note
查看程序正文是一次**内容外流**，会写进审计日志（`version.view`）。
这不是为了防谁，而是为了在追溯时能回答"这份程序都有谁看过"。
:::

## 第四步：把程序绑定到机台 {#assignment}

程序详情页 → **机台分配 → 新建分配**。一条分配回答的是：

> 这个程序，放到那台机床上时，**叫什么名字、放在哪个目录、需要做什么转换**。

| 字段 | 说明 |
| --- | --- |
| 机台 | 目标机床 |
| 机台文件名 | 机床上的文件名，例如 FANUC 用 `O1001`、西门子用 `DG3320_OP20.MPF` |
| 机台目录 | 留空则用这台机床的文件根目录 |
| 转换 | 落地前对内容做的处理，见下 |

**转换**共四项，都是可选的：

| 转换 | 作用 |
| --- | --- |
| 程序名改写 | 把内容里的程序名行改写成目标名——**FANUC 必须用**，见下 |
| 保证 `%` 包裹 | 内容首尾补上 `%` 行 |
| 行结束符 | `LF` 或 `CRLF` |
| 目标编码 | 机床侧的字符编码 |

:::danger[FANUC 的程序名来自内容，不是文件名]
FANUC 控制器**忽略传入的文件名参数**，程序名取自内容中第一个和第二个换行符之间的那一行
（`O1001(PUMP BODY ROUGH)` 或 `<NAME>` 形式）。

所以给 FANUC 机床做分配时，**必须**设置"程序名改写"为目标 O 号，
否则程序会以内容里原来的号落地，而不是你以为的那个号。
详见[机床系统差异](/reference/vendors/)。
:::

分配建好后可以点**预览转换**，看到实际会发送到机床的字节内容和它的 SHA-256——
这个哈希和下发记录里的"转换后哈希"应当完全一致。

## 第五步：下发 {#deploy}

在已发布的版本行点**下发**，勾选目标分配（可以多选，一次批量下发到多台机床），
选择是正式下发还是[试制](/guide/trials/)。

下发进入队列，由 `worker` 串行执行[事务式传输](/guide/transfer/)。
在**传输记录**页可以看到每一条的状态：

![传输记录](/img/console/deployments.png)

**成功（已校验）** 意味着：机床上现在的内容，回读出来与发送的内容逐字节一致
（经过厂商相关的归一化）。这时候才可以让操作工按启动。

## 第六步：让操作工在机边确认 {#shopfloor-check}

打开机边操作台 `http://<主机>:8030/shopfloor/`，用操作工账号登录，
选到这台机床，应该看到程序卡片显示**机床上已是最新版本**：

![机边操作台](/img/shopfloor/machine.png)

<p class="shot-caption">绿色边条的两个程序机床上已是最新版；红色那个被操作工改过，等工艺处置</p>

到这里，一条完整链路就走通了：
**上传 → 审批 → 发布 → 分配 → 下发 → 回读校验 → 机边确认**。
