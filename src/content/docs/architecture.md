## 3.1 适用范围 {#scope}

本章规定 DNC Pro 系统的部署形态、内部组成与外部接口关系，用于实施前的方案确认与
运行期的故障定位。

本系统不直接连接机床。与机床的全部通信经由彼络物联网关的
[HTTP 协议](https://docs.bivrost.cn/gateway-protocol)完成，包括列目录、读文件、写文件、
删文件、读取当前运行程序等操作。该设计带来两项结果：

a) 厂商差异由网关吸收。FANUC、西门子、三菱、兄弟的文件系统语义差异较大，
   网关已将其统一为一套接口，本系统的处理差异见 [6.2](/reference/vendors/)；

b) 一套本系统可管理多个车间。每个车间部署一台网关，本系统侧仅增加一条网关记录。

## 3.3 容器组成 {#containers}

整套系统以 docker compose 交付，仅支持 Linux 主机。各服务的职责按表 3-1 的规定。

<p class="tbl-caption">表 3-1　服务组成</p>

| 服务 | 职责 |
| --- | --- |
| `api` | REST API 主机，同时提供两个前端页面（`/` 管理控制台、`/shopfloor/` 机边操作台） |
| `worker` | 后台执行器：传输队列、滚动镜像调度、Webhook 投递、试制到期扫描 |
| `postgres` | 全部结构化数据：程序元数据、版本、机台、传输记录、审计链 |
| `backup` | 定时执行 `pg_dump` 与程序内容归档，按保留天数自动清理 |

程序正文不存入数据库，而存放于按内容哈希寻址的 blob 存储（`/data/blobs` 卷）。
内容相同的版本天然去重，历史快照的存储成本远低于逐份保存。

:::note[说明]
`api` 与 `worker` 可按任意顺序启动。数据库结构迁移在启动时经咨询锁自动完成，
不会出现两侧同时变更表结构的情形。
:::

## 3.4 后台循环 {#loops}

`worker` 服务中运行三个互不阻塞的循环。各循环的周期决定界面数据的更新时机。

### 3.4.1 传输执行器 {#transfer-executor}

自传输队列取出任务，对单台机台串行执行事务式下发（见 [5.4](/guide/transfer/)）。
处于下发中的机台不会同时被镜像读取，滚动镜像始终向真实传输让路。

### 3.4.2 滚动镜像调度 {#mirror-scheduler}

持续轮转扫描整个机队。每台网关同一时刻仅扫描一台机床，请求之间设节流间隔（默认 250 ms），
空闲时休眠（默认 5 s）后重新开始。执行规则如下：

a) 跳过当前正在运行的程序；

b) 每成功完整扫完一台机床后，更新该机台的「最近校验」时刻；

c) 扫描失败时记录到该机台并在控制台显示，不仅写入日志。

### 3.4.3 试制到期扫描 {#trial-sweep}

默认每 60 秒将超时的「试制中」记录标记为「已过期」。

:::caution[注意]
到期扫描仅改变状态标记，不改动机床上的内容。撤回与转正均须由人员执行，
见 [5.5](/guide/trials/)。
:::

## 3.5 数据流转 {#lifecycle}

一个版本的完整流转见图 3-3。

```text
  CAM 后处理 / 手工编写
        │
        ▼  上传（REST 或控制台）
   ┌─────────┐  提交审批   ┌──────────┐  批准    ┌──────────┐
   │  草稿   ├────────────►│ 待审批   ├─────────►│ 已发布   │
   └─────────┘             └────┬─────┘          └────┬─────┘
        ▲                       │ 驳回                │ 下发
        │                       ▼                     ▼
        │                  ┌─────────┐        ┌───────────────┐
        │                  │  草稿   │        │  机床上的文件  │
        │                  └─────────┘        └───────┬───────┘
        │                                             │ 操作工改了
        │        滚动镜像捕获（origin = 机边捕获）      │
        └─────────────────────────────────────────────┘
```

<p class="shot-caption">图 3-3　版本的数据流转</p>

同一流程亦适用于采纳：机床上原本未受管的文件可采纳进指定程序库，
以采纳基线作为 v1 纳入受控管理，见 [5.6](/guide/mirror/#adopt)。

## 3.6 与彼络物联网关的职责划分 {#gateway-split}

<p class="tbl-caption">表 3-2　与网关的职责划分</p>

| 事项 | 网关负责 | 本系统负责 |
| --- | :---: | :---: |
| 与机床通信（协议、编码、超时、重连） | <span class="sup-y">✓</span> | <span class="sup-n">✗</span> |
| 采集产量、OEE、报警、刀具数据 | <span class="sup-y">✓</span> | <span class="sup-n">✗</span> |
| 程序版本、审批、权限 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |
| 下发的事务性与回读校验 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |
| 全机队滚动备份与历史快照 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |
| 审计与合规追溯 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |

网关自带的[程序传输](https://docs.bivrost.cn/gateway/usage/file-transfer/)页面仍可使用，
适用于调试与一次性操作。本系统是其受控上层。

## 3.7 系统要求 {#requirements}

a) Linux x86-64 主机，内存不低于 4 GB；机队规模超过 30 台时不低于 8 GB；

b) Docker Engine 24 或更高版本，compose v2；

c) 自本主机至每一台彼络物联网关的网络可达（HTTP，80 端口）；

d) 具备固定 IP 或 DNS 名称，供车间浏览器与触摸屏访问。

:::danger[警告]
不支持将 Windows Server、WSL2 与 Docker Desktop 作为生产部署目标。
:::

安装方法见 [4.1](/start/install/)。
