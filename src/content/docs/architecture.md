DNC Pro **不直接连机床**。它把所有与机床的对话都交给彼络网关，
通过网关的 [HTTP 协议](https://docs.bivrost.cn/gateway-protocol)完成列目录、读文件、
写文件、删文件、读当前运行程序等操作。这带来两个好处：

1. **厂商差异由网关吸收。** FANUC、西门子、三菱、兄弟的文件系统语义天差地别，
   网关已经把它们统一成一套接口。
2. **一台 DNC Pro 可以管多个车间。** 每个车间一台网关，DNC Pro 侧只是多注册一条记录。

## 四个容器 {#containers}

整套系统以 docker compose 交付，只支持 **Linux 主机**：

| 服务 | 职责 |
| --- | --- |
| `api` | REST API 主机，同时提供两个前端页面（`/` 控制台、`/shopfloor/` 机边操作台） |
| `worker` | 后台执行器：传输队列、滚动镜像调度、Webhook 投递、试制到期扫描 |
| `postgres` | 全部结构化数据：程序元数据、版本、机台、传输记录、审计链 |
| `backup` | 定时 `pg_dump` + 程序内容归档，按保留天数自动清理 |

程序**正文**不进数据库，存放在按内容哈希寻址的 blob 存储（`/data/blobs` 卷）里——
相同内容的版本天然去重，历史快照的存储成本远低于逐份保存。

:::note
`api` 和 `worker` 可以任意顺序启动。数据库结构迁移在启动时通过咨询锁自动完成，
不会两边同时改表。
:::

## 三个后台循环 {#loops}

`worker` 里跑着三个互不阻塞的循环，理解它们有助于理解界面上"多久会更新"：

### 传输执行器 {#transfer-executor}

从传输队列取任务，对单台机床串行执行[事务式下发](/guide/transfer/)。
下发中的机床不会同时被镜像读取——**镜像永远给真实传输让路**。

### 滚动镜像调度 {#mirror-scheduler}

不停地轮转整个机队，每台网关同一时刻只扫一台机床，请求之间有节流间隔
（默认 250ms），空闲时休眠（默认 5s）后重新开始。它会：

- 跳过**当前正在运行的程序**（不去打扰加工）
- 在每次成功完整扫完一台机床后，更新这台机床的"最近校验"时间
- 扫描失败时**记录到这台机床上**并在控制台显示，而不是只写进日志

![设备页](/img/console/fleet.png)

<p class="shot-caption">卧加01 的镜像失败被记在行内（备份失败: Machine offline.），不必去翻日志</p>

### 试制到期扫描 {#trial-sweep}

默认每 60 秒把超时的"试制中"标记为"已过期"。
**过期只是改状态，从不动机床**——撤回或转正都需要人来点。

## 数据流：一个版本的一生 {#lifecycle}

```text
  CAM 后处理 / 手工编写
        │
        ▼  上传（REST 或控制台）
   ┌─────────┐  提交审批   ┌──────────┐  批准    ┌──────────┐
   │  草稿   ├────────────►│ 待审批   ├─────────►│ 已发布   │
   └─────────┘             └────┬─────┘          └────┬─────┘
        ▲                       │ 驳回                │ 下发
        │                       ▼                     ▼
        │                  ┌─────────┐        ┌───────────────┐
        │                  │  草稿   │        │  机床上的文件  │
        │                  └─────────┘        └───────┬───────┘
        │                                             │ 操作工改了
        │        滚动镜像捕获（origin = 机边捕获）      │
        └─────────────────────────────────────────────┘
```

同一条流程也适用于**采纳**：机床上原本无人管的文件可以一键"采纳"进某个程序库，
以采纳基线作为 v1 进入受控世界。

## 与彼络网关的分工 {#gateway-split}

| 事项 | 网关负责 | DNC Pro 负责 |
| --- | :---: | :---: |
| 与机床通讯（协议、编码、超时、重连） | <span class="sup-y">✓</span> | <span class="sup-n">✗</span> |
| 采集产量 / OEE / 报警 / 刀具 | <span class="sup-y">✓</span> | <span class="sup-n">✗</span> |
| 程序版本、审批、权限 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |
| 下发的事务性与回读校验 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |
| 全机队滚动备份与历史快照 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |
| 审计与合规追溯 | <span class="sup-n">✗</span> | <span class="sup-y">✓</span> |

网关自带的"[程序传输](https://docs.bivrost.cn/gateway/usage/file-transfer/)"页面依然可用，
适合调试和一次性操作；DNC Pro 是它的受控上层。

## 系统要求 {#requirements}

- Linux x86-64 主机，最低 4 GB 内存（机队超过 30 台建议 8 GB）
- Docker Engine ≥ 24 与 compose v2
- 从这台主机到每一台彼络网关的网络可达（HTTP，80 端口）
- 一个固定 IP 或 DNS 名（车间浏览器要打开它）

:::caution
不支持 Windows Server、WSL2 和 Docker Desktop 作为**生产**部署目标。
:::
